**Root Cause**

- The **email service** is running a **Puma** web server configured with **only 5 worker threads** (`Min threads: 0, Max threads: 5`).  
- Under the load generated by the demo (load‑generator pod), the email service receives more concurrent HTTP requests than it can handle. Puma’s request queue fills, causing the server to return **HTTP 408 (Request Timeout)** for some requests.  
- The frontend (and downstream checkout flow) receives these 408 responses, logs them as **“shipping quote failure … got 408”**, and aborts the checkout process.  

**Evidence Supporting the Root Cause**

1. **Frontend logs** – 68 occurrences of `Error: 13 INTERNAL: shipping quote failure: failed POST to email service: expected 200, got 408`.  
2. **Email pod logs** – All recorded POSTs return **200**; no 408s are logged on the server side, indicating the timeout is generated by the server before processing the request.  
3. **Puma startup log** – Shows the server is limited to **5 threads**, which is insufficient for the concurrent request volume generated by the demo.  
4. **Jaeger traces** – Show the frontend’s HTTP calls to the email service ending with status **408**, confirming the timeout originates at the email endpoint.  

**Recommended Fix**

1. **Increase Puma thread pool** for the email service:  
   - Set environment variables (or modify the Docker entrypoint) to raise `WEB_CONCURRENCY` / `MAX_THREADS` (e.g., `MIN_THREADS=5`, `MAX_THREADS=20`).  
   - Alternatively, adjust the `puma.rb` configuration to allow more concurrent connections.  

2. **Scale the email deployment** (optional):  
   - Increase the replica count (`kubectl scale deployment email --replicas=2`) to distribute load across multiple pods.  

3 **Verify after change**:  
   - Observe the frontend logs for the disappearance of 408 errors.  
   - Check Puma metrics (if exposed) or Prometheus `puma_thread_pool_size`/`puma_active_requests` to confirm the thread pool is no longer saturated.  

**Impact Classification**

- **Affected**: `frontend` pod (receives 408 errors), `checkout` flow (fails due to email timeout).  
- **Checked, healthy**: All other micro‑services (accounting, cart, product‑catalog, etc.) – no errors or readiness failures observed.  
- **Changed during the window for another reason**: None identified.  

**Bottom Line**

The broken behavior in the OpenTelemetry Demo Astronomy Shop is caused by the **email service’s under‑provisioned Puma thread pool**, which leads to **HTTP 408 timeouts** under load, breaking the checkout flow. Increasing the thread pool (and optionally scaling the deployment) will resolve the issue.
